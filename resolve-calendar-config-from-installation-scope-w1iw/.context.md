# Goal
Keep Calendar account metadata and credentials private even when the extension source or Pi dotfiles are version-controlled.

# Priority
P0 — privacy release blocker.

# Storage Decision
Use a service-specific private application-data directory:
- macOS: ~/Library/Application Support/pi-google-calendar/
- Linux: ${XDG_DATA_HOME:-~/.local/share}/pi-google-calendar/
- Windows: %LOCALAPPDATA%/pi-google-calendar/
- Override: PI_GOOGLE_CALENDAR_DATA_DIR

# Layout
- oauth-client.json — the user's Google OAuth client ID/secret
- accounts.json — stable account IDs, verified display emails, and health metadata; no OAuth tokens
- tokens/<stable-subject-hash>.json — one account's OAuth tokens per file; email is not used as a filename

# Definition of Done
- Nothing is written into the extension checkout, project repository, or ~/.pi
- Directories use mode 0700 and credential/metadata files use mode 0600
- Writes are atomic and protected against concurrent Pi processes
- Debug logs and auth URLs never contain token or authorization-code values
- Storage corruption identifies the affected account without leaking credentials
- Tests verify platform paths, override handling, modes, atomicity, locking, and recovery
- Existing ~/.pi/google-calendar data has an explicit one-time migration or manual remove/re-add path

# Deferred
Migration to Pi-native credential ownership and OS keychain encryption are separate later decisions.
